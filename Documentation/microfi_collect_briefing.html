01

The pitch — first two minutes

Open with the problem, not the product. This audience has built collection/ledger systems before — they'll trust you faster if you show you understand the domain pain before the tech.

The problem. Across CEMAC-region microfinance institutions, field agents still collect client cash the old way: a paper booklet, a physical stamp, a walk back to the branch at day's end. Cash discrepancies surface days later, if at all. There's no live visibility into where an agent is, what they're holding, or whether today's cash matches what the ledger expects — until someone manually counts.

What MICROFI COLLECT is. A digital layer in front of the institution's existing Core Banking System — not a replacement for it. An offline-first Flutter app for field agents, a matching client-facing digital booklet, and a Next.js Back-Office for supervision and end-of-day reconciliation. The CBS stays authoritative for the actual ledger; MICROFI owns the field-collection workflow, escrow accountability, and real-time oversight around it.

Say this

"Everything you're about to see assumes the network isn't reliable and the phone might die mid-collection — because in the field, both of those are the normal case, not the edge case."

03

Architecture, in one breath

One Spring Boot 4 core backend owns every business rule — agents, escrow, collections, tracking, OFJ, client tokens. A separate Spring Boot service, the CBS Middleware, owns only vendor-specific mapping to whichever core banking system the institution runs (Amplitude, FinanSoft, or others) — so the core never hard-codes one bank's wire format. Kong sits in front as the API gateway (TLS, rate-limiting, JWT). Postgres is the single source of truth; RabbitMQ decouples the core from the CBS so a slow bank integration never blocks a mobile request.

Say this

"We chose a modular monolith with one isolated adapter, not microservices — and I'll come back to why that was deliberate, not a shortcut, in a few minutes."

UC-01 · FR-01

Agent Authentication & Device Binding

The workflow
  1. Agent logs in with a username/password issued at enrollment — no separate "register this device" step exists.
  2. Their very first successful login is the enrollment: whichever phone sent it gets its IMEI bound automatically.
  3. Every login after that must present the same IMEI, or it's rejected outright — a stolen password alone is not enough.
  4. Phone lost or broken → an ADMIN/BRANCH_MANAGER runs Reset Binding with a mandatory reason on file.
  5. Agent's next successful login, from whatever phone they now have, re-binds automatically — no code sent, nothing out of band.
How it's built

AuthenticationController.login() branches three ways on agent.imei: already bound → strict match or reject; unbound + branch requires binding → bind whatever device just authenticated; unbound + not required → skip entirely.

Reset is PATCH /agents/{id}/device-binding — clears imei, stamps deviceResetReason + deviceResetAt for audit. Password and PIN are untouched by design; this is purely a device concern.

UC-06 – UC-08, UC-12 · FR-06, FR-07, FR-08, FR-12

Cash Collection — the core loop

The workflow
  1. Agent searches and locks a single client before anything else can happen.
  2. GPS is checked first — if there's no valid fix, the collection wizard simply doesn't open.
  3. Agent counts physical notes/coins by denomination; the running total previews against their remaining daily ceiling live.
  4. Confirms with their own transaction PIN (never the login password).
  5. Online → posts immediately. Offline → the record sits in an encrypted local queue and syncs the moment connectivity returns.
How it's built

The server never trusts the client's GPS gate alone — CollectionService.recordCollection() re-validates coordinates and re-enforces the escrow ceiling independently.

(agentId, deviceTxId) is a unique constraint, so a retried offline sync can never double-count. Denomination counts are normalized rows, not a JSON blob, so end-of-day can reconcile line by line.

Offline queue moved this session from plaintext shared_preferences to AES-encrypted flutter_secure_storage — cash data sitting unencrypted on a lost phone was a real compliance gap.

UC-03 – UC-05 · FR-03, FR-04, FR-05

Escrow Wallet & Ceiling

The workflow
  1. Every new agent starts with a zero-balance escrow account — they can log in, but can't collect a single franc yet.
  2. An admin funds it with the agent's real cash security deposit, and must attach proof of that deposit — mandatory, every top-up.
  3. Funding for the first time is what activates the agent — there is no separate "activate" button.
  4. Collection ceiling tracks the deposit 1:1 by default, adjustable per branch policy.
  5. An admin can grant a temporary ceiling override for a single day, with a mandatory justification on file.
How it's built

EscrowService.topUp() credits balance and raises ceiling in one transaction, then calls activateIfPendingCeiling() as a side effect the moment ceiling crosses zero — activation isn't a separate code path, it falls out of the funding logic.

Deposit proof is a multipart upload stored per EscrowLedger row via a small dedicated storage service. The ledger itself is append-only — no updates, no deletes on financial facts, ever.

UC-09 · FR-09

Multi-Channel Notification & Receipt

The workflow
  1. The instant a collection validates, a Flash SMS attempt fires to the client.
  2. The agent can print a receipt on a paired Bluetooth thermal printer, or download a styled PDF straight to the phone.
  3. Either channel failing never invalidates the collection — it already succeeded before notification was attempted.
How it's built

NotificationService.prepare() composes two representations from the same data: a fixed 32-column plain-text block for ESC/POS thermal printing, and structured JSON that the app renders into a real PDF client-side — brand mark, denomination table, a scannable QR of the transaction reference.

Built the whole PDF path this session, and hit a genuine library pitfall along the way: BorderRadius.circular(999) — the usual CSS "always fully rounded" trick — isn't clamped by the PDF renderer the way a browser clamps it, so it briefly drew as giant distorted spikes instead of pill badges. Fixed by sizing the radius to the actual element height instead of a large constant.

UC-16 – UC-18 · FR-16, FR-17, FR-18

End of Day — the Digital Cash Desk (OFJ)

The workflow
  1. Cashier opens the desk and sees each agent's digital total — what the app recorded all day.
  2. Physically counts the cash each agent hands in and enters it.
  3. System computes Δ = physical − digital, per agent, live.
  4. Zero delta closes clean; a shortage becomes a formal debt against that agent with a mandatory comment and an immutable audit trail.
  5. The session can't close with a pending offline queue anywhere in the branch, or an unresolved shortage.
How it's built

One OfjSession per branch per business date, auto-created on the day's first read. Close is gated by two independent checks: hasPendingUnsyncedCollections() — a cross-module read, since an unsynced device is invisible to the digital total and would silently understate it — and every line resolved.

Variance recording only accepts negative deltas (shortages) by rule, and writes an immutable VarianceDebt row.

UC-19 – UC-22 · FR-19 – FR-22, BR-04

Client Digital Booklet & Two-Party Activation

The workflow
  1. Client sets their own login/PIN using a CBS-issued Activation ID — proves they're really who the ID says.
  2. Independently, the field agent who took their activation cash sponsors it — either action can happen first.
  3. The digital token — and the balance/history it unlocks — is issued only once both sides are done.
  4. After the annual token expires, the client can still view profile, balance, and history read-only — visibility of money is never gated by token status.
How it's built

Both actions write to the same ActivationRequest row (sponsoredAt / paidAt); a shared finalizeIfReady() fires from whichever side lands second, issuing the token and triggering the CBS fee split exactly once regardless of order.

Caught and fixed a real cross-module bug here this session — a "has this already happened" check was inferring the answer from local data instead of querying the module that actually owns it. The unit-test mock had the same blind spot the code did, which is why it slipped through the first time.

UC-10, UC-11, UC-13, UC-14 · FR-10, FR-11, FR-13, FR-14

Field Tracking, Geofencing & SOS

The workflow
  1. Agent app pings location periodically in the field — not a continuous stream.
  2. Back-Office renders each agent's route plus that day's collection markers on a live map.
  3. A branch manager can draw a geofence polygon per agent; stepping outside it raises an alert with elapsed time tracked until they return.
  4. A dedicated SOS button sends a high-priority distress signal with location — separate from routine tracking, and the agent can't disable it.
How it's built

Pings are periodic by design, explicitly to protect the ≥8h battery-autonomy target — continuous streaming was ruled out early. Geofence breach is a standard point-in-polygon test against stored vertices.

Fixed the live map's sidebar ordering this session too: suspended agents are excluded from the field-units list entirely, and agents who've just collected now surface first, most-recent collection at the top.

04

What's actually interesting here

This is the section this specific audience will remember. Lead with the trade-offs, not the feature list.

Modular monolith, isolated CBS adapter

One deployable owns every business rule; only vendor-specific CBS wire formats live in a separate service. The core never depends on one bank's API shape — swapping CBS vendors touches the adapter, not the platform.

Hybrid reactive / ACID

WebFlux for high-concurrency, low-stakes paths — auth, sync, notifications. Spring Data JPA with strict transactions for anything money-moving. Throughput where it's cheap, consistency where it's not negotiable.

Offline-first as architecture, not fallback

The phone is the system of record during the business day; the server reconciles at sync and at EOD. This one decision shapes idempotent device-tx-ids, server-side re-validation of client-captured GPS, and the encrypted local queue.

Layered accountability

IMEI binding, transaction PIN, and login password are three independent factors across device / transaction / account. Financial facts are immutable — no soft-deletes, no updates on ledger rows — by design, not convention.

05

Anticipated questions

This audience has built similar systems — expect these specifically.

Why not microservices?

One team, one deployable, one database — the actual complexity here is business-rule complexity, not scaling complexity. The one place vendor lock-in genuinely bites (CBS wire formats) is already isolated into its own service. Splitting further would buy deployment overhead without buying anything real.

What happens if an agent's phone dies mid-collection, with unsynced data?

The queue is encrypted at rest, so a lost device isn't a data-leak risk. End-of-day close is hard-blocked while any agent in the branch still has a pending offline queue — the branch physically cannot close the books on cash the server hasn't seen yet.

How do you stop a retried offline sync from double-counting?

Every collection carries a client-generated device transaction ID; (agentId, deviceTxId) is a unique constraint server-side. A retry is a no-op, not a duplicate.

How do you actually reconcile against the bank?

The CBS Middleware adapter owns that mapping, and RabbitMQ decouples it from the core — a slow or down CBS integration never blocks a mobile request. Daily export posts the closed OFJ session's totals once reconciliation is done, not before.

What stops a cloned app or shared password from being used?

IMEI binding. A correct password alone doesn't get you in from a second device — the account is locked to whichever phone it first bound to, until an admin explicitly resets it with a reason on file.

06

Honest gaps — say these before they ask

A peer audience trusts candor about known gaps more than a polished claim of completeness.

  • FR-06 QR-code client identification isn't built yet — the one remaining MVP functional requirement still open.
  • CBS Core banking integration is currently mocked. The client app's account balance is deliberately hidden right now specifically because it isn't backed by a real CBS yet — a recent, intentional call, not an oversight.
  • SMS No real carrier credentials wired up locally — sends are best-effort no-ops in this environment. The gateway abstraction is ready for real Orange/MTN endpoints; it's a config change, not a rebuild.
