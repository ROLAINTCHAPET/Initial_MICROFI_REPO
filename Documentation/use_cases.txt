Business Rules

Authenticate the Collection Agent on the mobile terminal to grant access to
field collection features.
Terminal powered on, MICROFI application launched, active agent
account.
Agent authenticated, local session established, access token generated.
1. The agent reaches the login screen of the mobile application.
2. The system displays the credentials form (User ID / PIN code).
3. The agent enters credentials.
4. The system validates credentials (locally offline or against the server if
online).
5. The system loads the agent’s profile and parameters.
6. The system displays the main collection dashboard.
4a: Invalid credentials: System displays ”Invalid User ID or PIN”, attempt
counter +1, returns to step 3.
4b: Locked account: System displays ”Account locked, contact your
manager”.
• Account locked after 3 consecutive failed attempts.
• Confidential PIN code (4 to 6 digits).
• Offline authentication backed by an encrypted local key.

UC02 – Register Client Deposit
UC02

Identifier

Register Client Deposit

Name

Collection Agent

Actor(s)

Record a cash deposit made by a client to the collection agent on the field.

Objective
Pre-conditions
Post-conditions
Nominal Scenario

Alternative
ios

Scenar-

Business Rules

Agent authenticated, collection session active.
Transaction saved in local database, physical receipt printed,
synchronization initiated if network is available.
1. The agent navigates to ”New Deposit”.
2. The system displays the transaction form.
3. The agent inputs the client’s account number and deposit amount.
4. The system automatically includes limit checking (UC03: Check
Transaction Limit).
5. The agent validates the transaction.
6. The system saves the transaction into local terminal storage.
7. The system automatically includes receipt printing (UC04: Print
Deposit Receipt).
8. The system displays ”Deposit registered successfully”.
4a: Limit exceeded: System displays an error message and blocks
validation.
8a: Network available: System triggers UC05 (Manual Synchronisation)
to push pending transactions to the backend.
• Client account identifier and amount are mandatory.
• Automatic timestamping and GPS tagging of each transaction.
• Validated transactions cannot be modified or deleted locally.

Business Rules

1.4

MICROFI — Use Case Specifications

Verify that the transaction amount complies with individual transaction
limits and the agent’s daily threshold.
Deposit amount entered by the agent.
Transaction authorized or rejected.
1. System retrieves the entered deposit amount.
2. System reads the agent’s configured limit parameters.
3. System computes the total accumulated deposits for the current day.
4. System checks if Amount ≤ Single Limit AND
Daily T otal + Amount ≤ Daily Limit.
5. System validates controls and allows deposit processing.
4a: Single limit exceeded: System returns refusal ”Amount exceeds
single transaction limit”.
4b: Daily limit exceeded: System returns refusal ”Agent daily limit
reached”.
• Limits are set by the Branch Manager during session opening.
• Enforcement performed locally without requiring network connection.

Issue a physical printed receipt to give to the client following a validated
deposit.

Physical receipt printed.
1. System generates receipt layout (Date, Time, Agent ID, Masked

• Printed receipt must include a unique encrypted security hash.

UC05 – Manual Synchronisation
UC05

Identifier

Manual Synchronisation

Name

Collection Agent

Actor(s)

Transmit locally stored offline transactions to the Back-Office database.

Objective
Pre-conditions
Post-conditions
Nominal Scenario

Alternative
ios

Scenar-

Business Rules

Agent authenticated, offline transactions pending, network connection
available.
Transactions uploaded, validated by server, and marked as ”Synchronized”
on the terminal.
1. The agent clicks ”Synchronize”.
2. System checks network connectivity.
3. System bundles un-synchronized local transactions into an encrypted
payload.
4. System sends payload to the Back-Office Middleware.
5. System receives server acknowledgment (ACK).
6. System updates local transaction statuses and displays
”Synchronization successful”.
2a: No network: System displays ”Network unavailable, try again later”.
5a: Transmission failure: System resends unconfirmed batches.
• Data retained locally until server acknowledgment is confirmed.
• Encrypted batch processing.

UC10 – Transaction Validation
UC10

Identifier

Transaction Validation

Name

Cashier, CBS (Core Banking System)

Actor(s)
Objective
Pre-conditions
Post-conditions
Nominal Scenario

Alternative
ios

Scenar-

Business Rules

Validate collected funds, reconcile physical cash with digital logs, and post
entries to the CBS.
Agent returned from field, session synchronized.
Session closed, variances computed, accounting entries posted to CBS.
1. Cashier selects an agent’s session to close.
2. System includes physical cash counting (UC10b: Bill Breakdown).
3. System includes automatic reconciliation (UC10a: Calculate
Cash-Digital Difference).
4. Cashier confirms session closure.
5. System transmits validated entries to the CBS for posting.
6. CBS returns confirmation acknowledgment.
7. System updates session status to ”Closed & Validated”.
3a: Variance detected: System executes extension UC10c (Flag
Suspicious Transaction).
5a: CBS timeout: System queues entries and notifies Cashier.
• Bill breakdown mandatory for session closure.
• Unresolved variances exceeding tolerance threshold must be flagged.

Sub-components for UC10:
• UC10a – Calculate Cash-Digital Difference (Included): Computes variance: V ariance = P hysicalCash−
DigitalT otal.
• UC10b – Bill Breakdown (Included): Captures physical banknote and coin counts by denomination
(10 000, 5 000, 2 000 FCFA, etc.).
• UC10c – Flag Suspicious Transaction (Extends): Marks session/transaction for audit if variance
exceeds threshold.
