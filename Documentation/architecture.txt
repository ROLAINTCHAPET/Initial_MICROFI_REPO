1. System Design Methodology
This document is the System Architecture and Software Design Document (SAD) for MICROFI.
It translates the Business Analysis & Requirements Specification (v3.1) into a concrete technical
architecture, technology stack, data model, interface contracts and deployable topology.

Inputs
• Business Analysis & Requirements Specification (AS-IS / TO-BE, stakeholders, RACI, FR-01 to
FR-22, NFR-01 to NFR-12, BR-01 to BR-04).
• Feature Priority Matrix and MVP boundary (6-week production window).
• CEMAC operational constraints: intermittent connectivity, low-literacy field users, COBAC/BEAC
traceability, agent commission economics (digital booklet).

Design Principles
1. Requirements traceability — Every architectural choice maps back to one or more FRs, NFRs
or BRs (e.g. offline-first ↔ FR-07 / NFR-01 / NFR-08; tokenised booklet ↔ FR-19 / BR-04).
2. Modular monolith + isolated CBS adapter — Core business logic stays in one Spring Boot
deployable with strict internal modules; vendor-specific CBS protocols live in a separate Spring
Boot middleware so the core never depends on Amplitude/FinanSoft wire formats.
3. Hybrid reactive / ACID — High-concurrency paths (sync, auth, notifications) use WebFlux;
money-moving paths use Spring Data JPA for strict transactional integrity.
4. Offline-first at the edge — The Flutter agent app is the system of record during the day; the
server reconciles on sync and at OFJ.
5. Security & compliance by design — STRIDE-driven controls: IMEI-bound sessions, JWT authenticity, AES-256 offline store, extbfmandatory GPS gate before any collection (BR-05 / FR12), non-repudiable geotags and OFJ audit, TLS everywhere, branch-scoped authorization, idempotent CBS posts; no mobile creation of CBS customers.
6. Observable operations — Metrics (Prometheus), logs (Loki), traces (Tempo) unified in Grafana
from day one.

Method Steps
1. Derive logical components from the TO-BE process and FR modules (agent terminal, client app,
back-office, core API, middleware, CBS).
2. Allocate each FR to a component and to an API surface (Core /api/v1 vs Middleware /mw/v1).
3. Define the relational schema that materialises entities implied by use cases (agent, collection,
denomination, ofj, access_token, . . . ).
4. Specify the technology stack per component and the production topology (Docker Compose +
observability).
5. Validate capacity and MVP scope against the Feature Priority Matrix (agent Digital Cash Desk
loop first; client activation and history as Fast-Follow where scored).

2. Global System Architecture
The platform follows a Modular Monolith & Event-Driven Hybrid Architecture. Both the core
business backend and the CBS integration middleware are implemented in Java Spring Boot 4
with Spring Data JPA. This keeps the entire server-side stack homogeneous, simplifies deployment,
and guarantees ACID consistency end-to-end while isolating CBS-specific adapters in a dedicated
service.

6. Database Schema
The Core Backend and the CBS Middleware share the same PostgreSQL instance but use separate
schemas (core and mw) to preserve clear ownership boundaries. All monetary amounts are stored
as integers in the smallest currency unit (XAF). Timestamps are stored in UTC (TIMESTAMPTZ).
Design rules: (1) No soft-deletes on financial facts — use status enums and immutable audit
rows. (2) Denomination breakdown is stored as structured JSONB and normalised lines
for reporting. (3) Client digital tokens never lock the underlying CBS balance; expiry only
restricts mobile transactional APIs.

Entity Relationship Overview
Entities are grouped into three independent domain columns. Relationships are strictly top → bottom inside each column. Cross-domain foreign keys (collection.agent_id, activation_payment.agent_id)
are noted in the table list below and are not drawn as crossing edges.

7. STRIDE Security Matrix
This section maps the classical STRIDE threat model to MICROFI’s architecture (Flutter edge, API
Gateway, Spring Boot 4 Core + Middleware, RabbitMQ, PostgreSQL, CBS). Each threat category is
linked to the security property it violates, the concrete system risks, and the design controls already
specified in the technology stack, schema and API surface.
Scope: Agent terminals (IMEI-bound), Client app (JWT + digital booklet token), Back-Office,
Core Backend, CBS Middleware, message broker and data at rest. Residual risk remains
where the platform depends on the external CBS and on physical custody of cash.

Unauthorized use of an agent terminal if IMEI binding is circumvented;
stolen or forged JWT presenting as a valid agent, client or back-office user;
reuse of a consumed Activation ID.

Design controls

FR-01 IMEI-bound SSO; Spring Security + JWT with short TTL and refresh;
biometric/PIN on device; single-use hashed Activation IDs; Gateway JWT
validation before routing.

Residual risk

Rooted devices, GPS spoofing apps, or physical SIM/terminal cloning outside
pure software control.

T — Tampering (Integrity)
Item

Detail

Threats

Modification of local offline collection payloads or SQLCipher/Hive stores
on a compromised handset; unauthorized change of historical ledger rows
or audit trails.

Design controls

AES-256 encrypted offline queue (NFR-01); immutable financial facts (status
+ append-only audit, no soft-delete of money); device_tx_id uniqueness;
denomination checksum; middleware idempotency keys before CBS post.

Residual risk

Advanced malware with key access on a jailbroken device before sync.

R — Repudiation (Non-repudiability)
Item

Detail

Threats

Agent denies a cash collection or variance debt; denial of a temporary ceiling
override or schedule change if trails are incomplete.

Design controls

BR-05 mandatory GPS gate; FR-12 invisible geotag on every validated deposit; OFJ ∆ and variance_debt tables; mandatory justification + approver
on ceiling overrides (FR-05); correlation IDs end-to-end; Loki log retention
with agent/branch identifiers.

Residual risk

BR-05 / FR-12 hard-block collection when GPS is denied; residual risk is
limited to agents who cannot work until location is enabled (operational,
not silent unlocated cash).

I — Information Disclosure (Confidentiality)
Item

Detail

Threats

Leak of PII, balances or digital booklet tokens in transit; exposure of CBS API
credentials in middleware configuration.

Design controls

TLS at the Gateway; TLS or mTLS for service-to-service and AMQP; secrets
via environment / Docker secrets (never hardcoded); branch-scoped data
access in Back-Office; token expiry does not expose extra fields beyond readonly balance/history.

Residual risk

Misconfigured RabbitMQ management UI or Grafana left internet-exposed
without auth.

D — Denial of Service (Availability)
Item

Detail

Threats

Flooding public API endpoints or offline sync ingress; CBS slowdown or outage creating cascading backlog.

Design controls

Gateway rate-limiting and IP allow-list; RabbitMQ buffering between Core
and Middleware; offline-first agent app continues local capture; Spring Retry

Residual risk

Prolonged CBS outage delays final ledger posting though field operations
continue.

E — Elevation of Privilege (Authorization)
Item

Detail

Threats

Broken object-level authorization (BOLA) allowing access to another
branch’s agents, clients or OFJ; concurrent offline sync races that exceed
escrow ceiling (BR-03).

Design controls

Server-side branch scope on every admin query; RBAC for admin roles; escrow lock evaluated on server at sync commit (not only on device); optimistic
locking / transactional check of cumulative cash vs ceiling; agent status SUSPENDED invalidates sessions.

Residual risk

Insider threat with legitimate elevated Back-Office credentials (process control, not software alone).

9. Human-Machine Interface (HMI) Design Choices
FIELD AGENT MOBILE INTERFACE

“Fat-Finger” & Low-Literacy Optimization. High-contrast colours, large touch targets (min.
48 dp), 3-step collection wizard, persistent sync-status banner, Bluetooth thermal printer. GPS
gate: if location services are off or no valid fix is available, the collection wizard does not open
and the agent is prompted to enable GPS (BR-05 / FR-12).
CLIENT MOBILE INTERFACE

Consumer-grade banking UI: balance, digital booklet status, contribution history, profile.
Read-only mode after token expiry — money visibility is never locked.
BACK OFFICE WEB INTERFACE

High-density grids, liquidity charts, confirmation modals for high-risk actions, geolocation
maps, audit logs.
